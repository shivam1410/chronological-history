# Spec — Chronological History Site

## Implementation goal

A static site (`site/`) plus a Python data pipeline (`pipeline/`) that turns
human-authored YAML and Wikidata-imported JSON into optimized JSON bundles the site
reads at runtime. No server, no runtime dependencies, no bundler.

## Current state

Empty directory, not yet a git repository. Everything is greenfield; there are no
existing patterns to match. Python 3.14, Node 20 (with built-in `node:test`), and
git 2.50 are available.

## Scope

Data model, validation, pipeline, Wikidata importer, curated seed dataset, timeline
renderer, year-slice view, search and filters, GitHub Pages deployment.

## Non-goals

Editing UI, backend, map view, framework adoption, npm runtime dependencies.

## Interfaces and contracts

### Year numbering (the single most error-prone rule)

- Years are signed integers in **historical** numbering: `-1` is 1 BCE, `1` is 1 CE,
  **there is no year 0**. Source files and display both use this convention.
- All arithmetic (durations, ages, interval overlap) converts to **astronomical**
  numbering first: `astro(y) = y + 1 if y < 0 else y`. There is exactly one pair of
  conversion functions, in `pipeline/model.py` and `site/js/format.js`, and they are
  directly unit-tested including the -1 → 1 boundary.
- Deep-time shorthand in source files: `"66 Ma"`, `"4.54 Ga"`, `"12 ka"` mean that many
  million / billion / thousand years **before 1950 CE** (the geological BP convention).
  The parser subtracts from astronomical 1950 and then converts to historical numbering,
  so `"66 Ma"` is historical year `-65_998_051` and `"12 ka"` is `-10_051`. The offset is
  immaterial at Ma/Ga scale but is applied uniformly so the round-trip stays exact.

### Fuzzy date

Every temporal bound is a bracket, never a bare number:

```python
@dataclass(frozen=True)
class Bound:
    min: int        # earliest plausible year
    max: int        # latest plausible year
    display: str    # human string, e.g. "c. 1398" or "5th c. BCE"
```

`min == max` means a precise date. Authoring shorthand accepted by the loader:

```yaml
start: 1526                      # precise
start: [1398, 1440]              # bracketed
start: {min: -500, max: 200, display: "c. 500 BCE – 200 CE"}
start: "66 Ma"                   # deep time
end: ongoing                     # -> max bound = current year, flagged ongoing
```

When `display` is absent the loader derives it (`"c. 1398–1440"`, `"66 Ma"`, `"1526"`).
Derivation is pure and tested.

### Entry

```python
@dataclass(frozen=True)
class Entry:
    id: str                 # stable kebab-case slug, unique, the primary key
    title: str
    kind: str               # from data/taxonomy/kinds.yaml
    regions: tuple[str,...] # >=1, each from data/taxonomy/regions.yaml
    start: Bound
    end: Bound
    importance: int         # 1..5, drives label density and year-slice ranking
    summary: str            # 1-3 sentences, required
    categories: tuple[str,...] = ()
    aliases: tuple[str,...] = ()      # feeds search (e.g. "Kabir Das", "कबीर")
    significance: str | None = None
    note: str | None = None           # used to name competing scholarly positions
    related: tuple[str,...] = ()      # entry ids; validated to exist
    sources: tuple[Source,...] = ()   # citations for the DATING claim
    texts: tuple[Source,...] = ()     # where to READ the work itself
    wikidata: str | None = None       # Qid
    confidence: str = "high"          # high | medium | contested
    origin: str = "curated"           # curated | wikidata
```

### `site/data/meta.json`

```json
{
  "generated": "2026-09-19T00:00:00Z",
  "counts": {"entries": 0, "curated": 0, "imported": 0},
  "yearRange": [-4540000000, 2026],
  "lanes": [{"id":"india","label":"Indian Subcontinent","color":"--lane-india",
             "order":2,"subRegions":["north-india","south-india","deccan"]}],
  "kinds": [{"id":"polity","label":"Polity"}],
  "categories": [{"id":"scripture","label":"Scripture"}],
  "eraBuckets": [{"id":"1500-1599","from":1500,"to":1599,"count":412}]
}
```

### `site/data/spine.json`

Complete interval index — the client computes overlap, search and year-slice from this
alone, with no further fetch. Array-of-arrays to keep bytes down:

```json
{
  "fields": ["id","title","kind","lane","sMin","sMax","eMin","eMax","imp","bucket","flags"],
  "rows": [["mughal-empire","Mughal Empire","polity","india",1526,1526,1857,1857,5,"1500-1599",0]]
}
```

`flags` is a bitfield: `1` = uncertain start, `2` = uncertain end, `4` = ongoing,
`8` = contested, `16` = imported.

### Reading links (`texts:`)

`sources:` cites the evidence for an entry's *dates*. `texts:` points at the work
itself, so a reader can go from "Ramayana, c. 500 BCE - 200 CE" straight to a full
translation. They are separate fields because they answer different questions and have
different trust requirements: a source has to be current scholarship, whereas a text
just has to be a faithful, freely readable edition.

The Internet Sacred Text Archive (`archive.sacred-texts.com`) is the main supplier:
public domain, stable URLs, no API and no machine-readable metadata, so the mapping is
hand-curated - roughly 40-60 scripture and `work` entries, not a scrape. Validation
treats `texts[]` exactly like `sources[]`: each needs a title and an http(s) url.

### `site/data/eras/<bucket>.json`

```json
{"bucket":"1500-1599","entries":{"mughal-empire":{
  "summary":"…","significance":"…","note":null,"display":"1526 – 1857",
  "regions":["north-india","deccan"],"categories":["empire"],
  "aliases":["Timurid Empire of India"],"related":["akbar","humayun"],
  "sources":[{"title":"…","url":"https://…"}],"wikidata":"Q33296"}}}
```

Bucketing rule (pure, tested): deep time uses fixed buckets
(`pre-cambrian`, `paleozoic`, `mesozoic`, `cenozoic-early`, `pleistocene`, `holocene-early`),
then `-3000..-1` and `0..1499` in 500-year buckets, then 100-year buckets to the present.
An entry is filed by the bucket containing its `start.min`.

### Time scale contract (`site/js/timescale.js`)

Pure, no DOM. **Anchored piecewise-logarithmic** in years-before-present. A pure log in
BP was prototyped and rejected: it gave the Pleistocene 34% of the bar and all of
recorded history only 12% — backwards for this site's purpose. Anchors let the budget be
allocated deliberately.

```
astro(y) = y + 1 if y < 0 else y
BP(y)    = 1950 - astro(y)          // negative after 1950; never clamped
sp(y)    = log10(BP(y) + 1000)      // +1000 keeps the argument positive past 1950
```

Anchors — `(year, unit)`, monotone in both coordinates:

```
(-4_540_000_000, 0.00)  (-541_000_000, 0.10)  (-66_000_000, 0.20)
(   -2_580_000, 0.30)  (      -11_700, 0.42)  (     -3_000, 0.52)
(         -500, 0.62)  (          500, 0.72)  (       1_500, 0.84)
(        1_800, 0.92)  (        2_026, 1.00)
```

Within a segment, interpolate linearly in `sp`-space; invert the same way per segment.
Monotonicity is guaranteed by construction (both coordinate sequences are increasing)
and is asserted directly by test over ~9000 sampled years.

**Verified budget** (measured, not estimated): deep time → K–Pg 20%, Cenozoic 10%,
Pleistocene/Ice Age 12%, early Holocene 10%, all recorded history 48% — of which
1500 CE → present is 16%. Round-trip error is under 1e-5 years at every anchor and at
`[-4.54 Ga, -66 Ma, -2.58 Ma, -11700, -500, 1, 1555, 1950, 2026]`. At a 1400 px canvas a
1500–1600 window resolves to ~2.9 years per pixel.

The `2026` anchor is the present; `ANCHORS[last]` is regenerated from the current year at
module load so the scale does not silently stop at a hardcoded date.

A **view** is a `[fromYear, toYear]` window rendered linearly in **unit space** — that is,
through `yearToUnit`, not through `sp` directly.

> **Corrected during Phase 1.** This section originally specified projecting linearly in
> `sp`-space. That is wrong and shipped as a real bug: projecting through `sp` bypasses the
> anchors entirely, and recorded history collapsed back to ~12% of the axis — precisely the
> pure-log behaviour the anchors exist to prevent. Inside one anchor segment `unit` is linear
> in `sp` anyway, so a zoomed window is still near-linear in years; across segments only unit
> space honours the budget. Two tests now assert the 48%/12% split directly against a view
> rather than against `yearToUnit` alone, so this cannot regress silently.

Exports:
`yearToUnit`, `unitToYear`, `createView(from,to,widthPx)`, `view.project(year) -> px`,
`view.unproject(px) -> year`, `view.zoomAbout(px, factor)`, `view.pan(px)`,
`view.ticks() -> [{year, label, major}]`.

Ticks are sampled at even intervals in unit space — so they are evenly spaced on screen —
then snapped to round values on a 1/2/5 × 10^k ladder. Three rules that a fixed-ladder
approach missed, each now covered by a regression test:

- the snapping step is capped at half the sample's own magnitude, or a sample at −430 Ma
  whose neighbours are a billion years away rounds to zero and every deep-time label piles
  onto the present;
- deep-time ticks snap in **years-before-present**, not in historical years, because the
  label shows a BP value — snapping the year gives `602 ka` instead of `600 ka`;
- the first and last samples span one interval, not two, so their spacing must not be
  halved, or they pick a finer step than the middle of the axis and leave gaps like
  `1553 1554 1556` in an otherwise even sequence.

When every sample agrees on one step the window is uniform and ticks are laid out on that
step directly, which keeps such sequences gap-free. Labels come from `format.js`:
`4.54 Ga`, `66 Ma`, `12 ka`, `500 BCE`, `1555`.

### Lane layout contract (`site/js/layout.js`)

`packLane(entries, view) -> {rows: Entry[][], hidden: number}` — first-fit interval
packing with a minimum 4 px visual gap converted to years via the view, entries sorted
by `sMin` then descending duration. Rows are capped (default 6); overflow is counted
into `hidden` rather than dropped silently.

### Year-slice contract (`site/js/slice.js`)

`activeIn(spine, year) -> Entry[]` returns entries whose `[sMin, eMax]` interval contains
`year`, using astronomical arithmetic. `groupByLane(entries, laneOrder)` returns ordered
groups with empty lanes omitted. Entries whose `sMin == year` or `eMax == year` carry a
`boundary` marker and sort first within their lane; remaining entries sort by descending
`importance`, then ascending `sMin`.

## Technical approach

1. **Authoring** — YAML under `data/curated/`, one file per theme, each a list of
   entries using the shorthand above.
2. **Import** — `python -m pipeline.cli import --topic <t>` runs a topic-scoped SPARQL
   query against `https://query.wikidata.org/sparql` with a descriptive User-Agent,
   caches raw JSON under `data/imported/.cache/` (git-ignored), normalizes to `Entry`
   shape with `origin: "wikidata"`, and writes `data/imported/wikidata-<topic>.json`
   (committed). Never runs at page load or in CI's build job.
3. **Merge** — imported entries are dropped when they collide with a curated entry,
   matched first on `wikidata` Qid, then on normalized title with overlapping date
   brackets. Collisions are reported in the build summary, never silently resolved.
4. **Validate** — see rules below. Any error aborts the build before emit.
5. **Emit** — write `meta.json`, `spine.json`, `eras/*.json` into `site/data/`,
   deterministically ordered so git diffs stay readable.
6. **Serve** — GitHub Actions publishes `site/` to Pages.

### Validation rules (each one its own test)

| Rule | Error |
|---|---|
| `id` unique across all sources | names both files and the id |
| `id` matches `^[a-z0-9]+(-[a-z0-9]+)*$` | names file and id |
| every `regions` value exists in the taxonomy | names id and unknown region |
| `kind` and every `categories` value exist in taxonomy | names id and unknown value |
| `start.min <= start.max <= end.max` and `start.min <= end.min` | names id and the bounds |
| `importance` in 1..5 | names id |
| `summary` non-empty and ≤ 400 characters | names id and length |
| every `related` id resolves to an existing entry | names id and dangling reference |
| `confidence` in {high, medium, contested} | names id |
| `contested` entries carry at least one source | names id |
| bracket wider than 200 years implies confidence ≠ `high` | names id and bracket width |
| every `sources[].url` is http(s) | names id and url |

## Architecture rationale

- **Vanilla ES modules, no framework.** The UI is one canvas plus two small DOM views.
  A framework would add a build step, a dependency tree, and an upgrade treadmill to a
  site whose whole point is to still work in ten years. ES modules load natively on
  Pages with no bundler.
- **Canvas, not SVG/DOM, for the timeline.** 20k DOM nodes with per-frame transforms
  would jank; canvas redraws only the visible window. Accessibility is preserved by the
  parallel hidden list rather than by using DOM for rendering.
- **Spine/detail split.** The spine must be complete because search and year-slice are
  interval queries over the whole dataset; prose must not be, because it dominates bytes.
  This keeps first paint small while keeping every query local and instant.
- **Bucketed detail, not hash-sharded.** Queries are temporally local — a year-slice or a
  zoomed window touches a handful of adjacent eras. Hash sharding would scatter one
  logical read across every shard.
- **Piecewise-log time.** Linear time makes 4.5 Ga unreadable; pure log makes recent
  centuries unreadable. `log10(BP + 1000)` is monotone, invertible, and gives the last
  two millennia about 7% of the full bar — dense enough to see, compressed enough to fit.
- **Curated-wins merge.** Wikidata's Indian chronology is thin and inconsistent on exactly
  the entries this site cares most about. Hand-authored data must never be overwritten
  by an import run.

## Decisions and alternatives considered

| Decision | Chosen | Rejected | Why |
|---|---|---|---|
| sacred-texts.com | curated `texts:` reading links | scraping it for dates | its translations are 1880s-1910s; their chronologies are a century stale and would degrade exactly the contested entries we bracket most carefully |
| Storage format | YAML source → generated JSON | SQLite + sql.js | ~1.5 MB wasm payload; binary blobs are not diffable or reviewable in git |
| Site framework | none (vanilla ESM) | Vue / React / Svelte | build step and dependency tree for a two-view site |
| JS test runner | `node --test` (built-in) | Vitest / Jest | keeps the repo at zero npm dependencies |
| Deep-time scale | piecewise-log in BP | linear; pure log; discrete era pages | only option that is both continuous and readable at every scale |
| Pages source | Actions publishing `site/` | `docs/` folder | `docs/` misnames the site; Actions also gates on tests |
| Date representation | bracket + display string | single year + ± tolerance | asymmetric ranges ("500 BCE – 200 CE") are the norm for scriptures |

## Failure modes

| Failure | Behavior |
|---|---|
| `spine.json` fetch fails | Error card naming the URL, with retry; app does not white-screen |
| An era bundle fetch fails | Panel still shows spine data plus "Details unavailable — retry" |
| Malformed source YAML | Build aborts with file, line, entry id, and rule; no bundle is written |
| Wikidata endpoint down or rate-limited | Importer exits non-zero with the HTTP status; committed `data/imported/` is untouched, so the site still builds |
| `localStorage` throws (private mode) | Theme read/write is wrapped in `try/catch`; site falls back to `prefers-color-scheme` |
| Entry interval outside the data range | Clamped by the view; validation warns |

## Invariants

- `site/data/` is always generated — never hand-edited. The build is deterministic:
  the same sources produce byte-identical output apart from the `generated` timestamp.
- Entry `id` is permanent. Renaming one breaks existing bookmarks and `related` links;
  changing an id requires updating every referrer, which validation enforces.
- The spine contains every entry. Any query the UI performs (search, year slice,
  visible-window culling) is answerable from the spine alone.
- Pure modules (`timescale`, `layout`, `search`, `slice`, `format`) never touch the DOM,
  `fetch`, or `localStorage`.

## Testing strategy

- **pytest** (`tests/`), one file per pipeline module. Behavior-level: parse a fixture
  YAML, assert the emitted bundle shape; assert each validation rule rejects its own bad
  input with a message naming the entry. Wikidata network calls are exercised against a
  recorded fixture response, never live.
- **`node --test`** (`site/js/*.test.js`), one file per pure module. Round-trip
  `yearToUnit`/`unitToYear`; monotonicity across the full range; the no-year-zero
  boundary; tick ladder selection at six representative zoom levels; lane packing with
  overlapping and nested intervals; `activeIn` at interval edges; search ranking.
- Behavior-changing work follows RED → GREEN → REFACTOR with the exact commands named
  in `tasks.md`.
- Manual acceptance: the nine PRD criteria, checked in a browser before the final commit.

## Verification targets

- `make test` runs both suites and exits non-zero on any failure.
- `make build` regenerates `site/data/` and reports entry counts per lane and per era.
- `make serve` starts `python3 -m http.server` rooted at `site/`.
- CI runs `make test` and `make validate` on every push.

## Observability

The build prints a summary table: entries per lane, per kind, per era bucket, curated vs
imported, merge collisions dropped, and the widest brackets — so dataset gaps are visible
without opening the files. The site logs nothing to the console in normal operation.

## Rollback

`site/data/` is committed, so reverting a bad data build is `git revert`. Pages
redeploys from the reverted commit. No migrations, no state.

## Acceptance criteria

The nine criteria in `prd.md`, plus: both test suites green, validation clean, and the
build summary showing ≥ 400 curated entries with every lane non-empty from 500 BCE on.
